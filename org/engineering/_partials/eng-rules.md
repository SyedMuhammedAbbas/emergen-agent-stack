## Engineering rules
- Follow `{{ENGINEERING_SKILL}}` (standards, references and checklists) for the project stack, and the project's own CLAUDE.md / AGENTS.md first: its conventions win.
- Branch per the project's own convention (its CLAUDE.md; NeuraX uses `task/<ID>-<slug>`). Only when it has none, use `agent/<ticket>-<slug>`. Branch from the project's integration branch (`staging` unless the project says otherwise) and open any PR **against that branch**: `gh pr create --base staging ...`, never the repo's default branch (`main` is production). Reference the Odoo ticket (Ticket#<n>) when there is one, and check `gh pr view --json baseRefName` after creating it. Never merge, never push to staging/main/master, never deploy to production, never touch production secrets or `.env` files. Merges are the owner's decision, and an approval hook enforces them.
- Commit as soon as the change compiles, and again after the targeted tests pass. While iterating, run only the tests for the files you changed; the slow full gate (e.g. `tool/verify.sh`, the whole `flutter test`) is for the final check, once.
- Follow the project's recorded architecture decisions (`DECISIONS.md`, ADRs, architecture docs) exactly; if you disagree, say so instead of deviating.
- Before handing off for review, run Gate 1 of `delivery-gate` on your own work and include the filled checklist in your report (and the PR description, if there is a PR). Incomplete work is reported as `STATUS: BLOCKED`, never as ready.
- Write the smallest complete change (the `ponytail` plugin is on in every session): no unrequested abstractions, no new code where existing code does the job. Before handing off, run `ponytail-review` on your diff, fix what it finds or say why not, and run the CI gate's own format and lint commands on the changed files (Flutter: `dart format --set-exit-if-changed` and `flutter analyze --fatal-infos`; Node: the repo's lint and prettier check). A build that fails on formatting is a failed change.
- Stage explicit paths only (`git add <path>`, never `git add -A` or `.`), never run a repo-wide `--fix` or formatter, and leave the working tree clean at the end.
- Tests follow `test-integrity`: written from the ticket's acceptance criteria, and every new or changed test is shown failing when the behaviour is broken (before the fix, or with the behaviour broken on purpose). Include both outputs under **"Proof the tests can fail"**; without it the change is not ready for review. Never loosen, skip or delete a test to get green.
- No new package, tool or script without the `tool-vetting` checklist and the owner's yes.
- Keep changes small. If scope grows, stop and propose a split to the owner.
